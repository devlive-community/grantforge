**접근 제어 → 신원 소스**에서 사용자가 로그인하는 데 사용할 디렉터리나 신원 제공자를 설정합니다. 이런 계정의 비밀번호는 신원 소스에 저장되며, GrantForge는 저장하지도 수정할 수도 없습니다.

![신원 소스](/screenshots/identity-sources.png)

## LDAP / Active Directory

"신원 소스 추가"를 클릭하고 타입은 "LDAP 디렉터리"를 선택합니다.

| 설정 | 설명 |
| --- | --- |
| 디렉터리 주소 | `ldap://` 또는 `ldaps://`, 여러 주소는 공백으로 구분하면 장애 조치가 가능합니다 |
| 사용자 Base DN | 예를 들어 `ou=people,dc=example,dc=com` |
| 조회 계정 | 사용자를 찾는 데 쓰는 계정(Bind DN)과 그 비밀번호입니다. 비워 두면 익명으로 조회합니다 |
| 사용자 필터 조건 | 기본값은 `(&(objectClass=person)(uid={0}))`이며, `{0}`은 사용자가 입력한 이름입니다 |
| 속성 | 사용자 이름, 표시 이름, 이메일, 고유 식별자의 속성입니다. 기본값은 OpenLDAP에 맞춰져 있고(`uid`, `cn`, `mail`, `entryUUID`), Active Directory에서는 `sAMAccountName`와 `objectGUID`를 입력합니다 |
| 새 사용자 계정 자동 생성 | 켜면 디렉터리의 사용자가 처음 로그인할 때 계정이 생성됩니다 |
| 동기화 간격 | 비워 두면 수동 동기화만 하며, 최소 간격은 15분입니다 |
| 디렉터리를 떠난 사용자 계정 비활성화 | 동기화할 때 디렉터리에 더 이상 없는 사용자를 비활성화합니다 |

저장한 뒤 **연결 테스트**를 클릭해 설정이 올바른지 확인합니다.

로그인할 때 GrantForge는 먼저 조회 계정으로 사용자를 찾고, 이어서 사용자가 입력한 비밀번호를 그 사용자 신원으로 디렉터리에 바인딩해 검증합니다.

**동기화**는 디렉터리의 새 사용자에 대해 계정을 생성하고, 기존 계정의 이름과 이메일을 업데이트하며, 설정에 따라 떠난 사용자를 비활성화합니다(그들의 세션도 함께 종료합니다). 동기화 결과는 신원 소스 카드에 표시됩니다.

## OpenID Connect

타입은 "OpenID Connect"를 선택하면 Keycloak, Azure AD, Okta, 다른 GrantForge 등에 연동할 수 있습니다.

| 설정 | 설명 |
| --- | --- |
| Issuer 주소 | 제공자의 발급자 주소입니다. GrantForge는 이 주소의 디스커버리 문서로 엔드포인트와 키를 가져옵니다 |
| 클라이언트 ID / 시크릿 | 제공자에 등록한 클라이언트입니다. 시크릿이 없으면 공개 클라이언트로 동작하며 PKCE를 사용합니다 |
| 콜백 주소 | 페이지에 표시되는 `<GrantForge>/api/v1/auth/federated/callback/<인코딩>` 주소이며, 제공자의 클라이언트에 등록해야 합니다 |
| 범위와 클레임 | 기본값은 `openid profile email`입니다. 사용자 이름, 표시 이름, 이메일은 각각 `preferred_username`, `name`, `email` 클레임에서 가져옵니다 |
| 휴대폰 번호 클레임 | 기본값은 `phone`(Casdoor)이며 다른 제공자는 `phone_number`로 설정할 수 있습니다. 휴대폰 번호를 동기화하려면 scope에 `phone`이 포함되어야 합니다. 로그인할 때 제공자가 번호를 반환하지 않으면 기존 번호를 유지합니다 |
| 아바타 주소 | OIDC 표준 `picture` 클레임에서 동기화하며 scope에 `profile`이 포함되어야 합니다. 반환되지 않으면 기존 아바타 주소를 유지합니다 |
| 인가 요청 추가 매개변수 | 선택 사항인 JSON 객체이며 값은 모두 문자열이어야 합니다. 예를 들어 Casdoor는 `{"provider_hint":"github"}`로 구성된 제공자를 지정할 수 있습니다. 매개변수는 브라우저 주소에 표시되므로 비밀 값을 넣지 마십시오 |

프로토콜 핵심 매개변수(`state`, `nonce`, `redirect_uri`, PKCE 매개변수 포함)는 GrantForge가 관리하며 추가 매개변수로 덮어쓸 수 없습니다.

활성화하면 로그인 페이지에 "<이름>으로 로그인" 버튼이 나타납니다. 사용자는 제공자에서 로그인한 뒤 GrantForge로 돌아오며, 2단계 인증을 켠 계정은 인증 코드도 입력해야 합니다.

## 계정 규칙

- 신원 소스 사용자의 고유 식별자(LDAP는 `entryUUID`/`objectGUID`, OIDC는 `sub`)는 GrantForge 계정 하나에 대응되며, 이름이 바뀌어도 대응 관계는 그대로입니다.
- 로컬에 같은 이름의 계정이 이미 있으면 **자동으로 연결하지 않으며**, 로그인이 거부됩니다. 관리자가 먼저 로컬 계정의 이름을 바꾸거나 삭제해야 합니다. 이렇게 하면 디렉터리의 동명 사용자가 기존 계정을 빼앗는 일을 막을 수 있습니다.
- 계정을 자동 생성하지 않는 신원 소스는 이미 연결된 사용자만 로그인하게 합니다.
- 신원 소스를 비활성화하면 그 사용자는 로그인할 수 없으며, 계정이 사용 중인 신원 소스는 삭제할 수 없습니다.
- 신원 소스 계정에도 평소와 같이 역할을 부여하고 2단계 인증을 켤 수 있습니다.

조직 구조 동기화는 별도의 데이터 소스에서 구성하며 OIDC 로그인 설정을 바꿀 필요가 없습니다.

## 데이터 소스와 조직 구조 동기화

데이터 소스는 조직 구조 동기화를 맡고, 신원 소스는 계속해서 OIDC 또는 LDAP 로그인을 맡습니다. 둘은 따로 구성하며 데이터 소스를 비활성화해도 OIDC 로그인에는 영향이 없습니다.

1. "액세스 제어 → 신원 소스"에서 기존 OpenID Connect 로그인을 구성합니다.
2. "액세스 제어 → 데이터 소스"에서 DingTalk 데이터 소스를 추가하고 연결할 OIDC 신원 소스를 선택합니다.
3. CorpId, AppKey, AppSecret과 시작 부서 ID(보통 `1`)를 입력합니다. AppSecret은 따로 암호화해 저장하며 API는 평문을 반환하지 않습니다. 편집할 때 비워 두면 기존 값을 유지합니다.
4. 로컬 부서 아래에 마운트할 수 있습니다. 동기화 간격은 기본 30분이며 15–10080분을 지정할 수 있고, 비우면 수동으로만 동기화합니다.
5. 저장한 뒤 연결을 테스트하고 첫 동기화를 실행합니다. DingTalk 애플리케이션에는 부서와 직원 주소록을 읽을 권한이 있어야 하며, 그 권한 범위가 선택한 하위 트리를 포함해야 합니다.
6. 사용자가 SSO로 로그인하면 신뢰할 수 있는 OIDC 이메일로 직원을 찾아 부서와 주 부서를 자동으로 채웁니다. 이메일은 관리자가 관리하고 직원이 다른 사람을 사칭해 쓸 수 없어야 하며 DingTalk 이메일과 같아야 합니다. 직원 이메일이 없으면 기업 이메일을 사용합니다.

로그인은 로컬 주소록 스냅숏만 읽고 DingTalk에 요청하지 않습니다. MFA를 사용하면 두 번째 단계 인증에 성공한 뒤 소속을 갱신합니다. 첫 동기화 전에 로그인한 계정은 신뢰할 수 있는 이메일을 임시로 보관했다가 동기화가 끝나면 연결합니다. 로컬에서 편집할 수 있는 프로필 이메일은 대조에 쓰지 않습니다. 없거나 중복되었거나 이미 다른 계정에 연결된 이메일로는 새 연결을 만들지 않습니다.

직원 연결은 외부 직원 ID로 고정되어 이메일이 바뀌어도 다른 직원에게 옮겨 가지 않습니다. 동기화는 여러 부서 소속도 다룹니다. 주 부서는 여전히 유효한 기존 주 부서를 우선 유지하고, 그렇지 않으면 안정적인 부서 ID 순서로 고릅니다. 로컬 부서, 사용자 그룹, 직책, 직접 역할 부여는 유지됩니다. 동기화된 부서에 역할을 할당하면 사용자는 기존 부여 규칙에 따라 역할을 상속하고, 부서를 옮기면 권한도 갱신됩니다.

조직 스냅숏이나 연결 대기 계정이 생긴 뒤에는 연결된 신원 소스, 기업, 애플리케이션, 시작 부서와 마운트 위치를 바꿀 수 없습니다. 동기화된 부서와 소속은 읽기 전용이며 사용자 관리나 조직 관리에서 직접 덮어쓸 수 없습니다. 사라진 부서는 기존 권한 부여를 지키기 위해 남겨 둡니다. 직원이 권한 범위의 주소록에서 빠지면 이 데이터 소스가 관리하는 소속을 제거하지만 계정을 자동으로 비활성화하지는 않습니다. 동기화된 부서를 가진 데이터 소스는 바로 삭제할 수 없고 대신 비활성화할 수 있습니다.

동기화는 모든 페이지를 가져온 뒤 원자적으로 적용합니다. 읽기 실패, 계층 이상, 권한 범위 변화가 있으면 마지막으로 성공한 스냅숏을 유지하며, 관리자는 동기화 요약, 이상 목록, 감사 기록으로 결과를 확인할 수 있습니다. 권한 범위가 바뀌었다면 원래 승인된 범위로 되돌린 뒤 동기화하십시오.

현재 [DingTalk 공식 서버 SDK](https://open.dingtalk.com/document/development/download-the-server-side-sdk)를 사용하며 HTTP 호출을 직접 구현하지 않습니다. 공급자 어댑터는 공통된 부서와 직원 스냅숏을 출력하므로, 나중에 Feishu 어댑터를 추가해도 같은 동기화, 연결, 권한 갱신 로직을 재사용할 수 있습니다.
