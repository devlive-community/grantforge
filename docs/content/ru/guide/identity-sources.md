**Управление доступом → Источники идентификации** настраивает каталоги и провайдеры идентификации, через которые пользователи могут входить. Пароли таких учётных записей хранятся в источнике идентификации: GrantForge не хранит их и не может их изменить.

![Источники идентификации](/screenshots/identity-sources.png)

## LDAP / Active Directory

Нажмите «Добавить источник идентификации» и выберите тип «Каталог LDAP»:

| Параметр | Описание |
| --- | --- |
| URL каталога | `ldap://` или `ldaps://`; несколько адресов разделяются пробелами для переключения при отказе |
| User Base DN | Например `ou=people,dc=example,dc=com` |
| Учётная запись для запросов | Учётная запись (Bind DN) и её пароль, которыми выполняется поиск пользователей; оставьте пустым для анонимных запросов |
| Фильтр пользователей | По умолчанию `(&(objectClass=person)(uid={0}))`, где `{0}` — имя, введённое пользователем |
| Атрибуты | Атрибуты для имени пользователя, отображаемого имени, почты и уникального идентификатора; значения по умолчанию подходят для OpenLDAP (`uid`, `cn`, `mail`, `entryUUID`), а Active Directory использует `sAMAccountName` и `objectGUID` |
| Автоматически создавать учётные записи для новых пользователей | Если включено, пользователь из каталога получает учётную запись при первом входе |
| Интервал синхронизации | Оставьте пустым, чтобы синхронизация выполнялась только вручную; минимум 15 минут |
| Отключать учётные записи пользователей, которых больше нет в каталоге | Во время синхронизации отключать пользователей, которых больше нет в каталоге |

После сохранения нажмите **Проверить подключение**, чтобы убедиться, что конфигурация верна.

При входе GrantForge сначала ищет пользователя учётной записью для запросов, затем проверяет пароль: сервер подключается к каталогу от имени этого пользователя с паролем, который тот ввёл.

**Синхронизация** создаёт учётную запись для новых пользователей каталога, обновляет имена и почту существующих учётных записей и — в соответствии с настройкой — отключает ушедших пользователей, одновременно завершая их сессии. Результаты синхронизации показываются на карточке источника идентификации.

## OpenID Connect

Выберите тип «OpenID Connect», чтобы подключить Keycloak, Azure AD, Okta, другой экземпляр GrantForge и другие провайдеры:

| Параметр | Описание |
| --- | --- |
| Issuer URL | Адрес издателя (issuer) у провайдера; GrantForge обнаруживает конечные точки и ключи по его discovery-документу |
| Client ID / secret | Клиент, зарегистрированный у провайдера; без секрета он работает как публичный клиент с использованием PKCE |
| Redirect URI | Значение `<GrantForge>/api/v1/auth/federated/callback/<код>`, показанное на странице; его нужно зарегистрировать у клиента провайдера |
| Scopes и claims | По умолчанию `openid profile email`; имя пользователя, отображаемое имя и почта берутся соответственно из claims `preferred_username`, `name` и `email` |
| Claim телефона | По умолчанию читается `phone` (Casdoor); для других провайдеров можно указать `phone_number`. Чтобы синхронизировать номер телефона, scope должен включать `phone`. Если при входе провайдер не вернул номер, сохраняется прежний |
| Адрес аватара | Синхронизируется из стандартного claim OIDC `picture`; scope должен включать `profile`. Если значение не вернулось, сохраняется прежний адрес |
| Дополнительные параметры запроса авторизации | Необязательный JSON-объект, все значения которого — строки. Например, для Casdoor можно указать `{"provider_hint":"github"}`, чтобы выбрать настроенного провайдера. Параметры видны в адресной строке браузера, поэтому не указывайте в них секреты |

Ключевые параметры протокола (включая `state`, `nonce`, `redirect_uri` и параметры PKCE) задаёт GrantForge; дополнительные параметры не могут их переопределить.

После включения на странице входа появляется кнопка «Войти через <название>». Войдя у провайдера, пользователь возвращается в GrantForge; у учётных записей с включённой двухфакторной проверкой дополнительно потребуется ввести код подтверждения.

## Правила учётных записей

- Уникальный идентификатор пользователя источника идентификации (`entryUUID`/`objectGUID` для LDAP, `sub` для OIDC) соответствует одной учётной записи GrantForge; переименование на это соответствие не влияет.
- Если локальная учётная запись с тем же именем пользователя уже существует, она **не связывается автоматически**: вход отклоняется, и администратор должен сначала переименовать или удалить локальную учётную запись. Так одноимённый пользователь из каталога не может забрать существующую учётную запись.
- Источник идентификации, который не создаёт учётные записи автоматически, пускает только уже связанных пользователей.
- После отключения источника идентификации его пользователи не могут входить; источник идентификации, который ещё используется учётными записями, удалить нельзя.
- С учётными записями источника идентификации можно обычным образом назначать роли и включать двухфакторную проверку.

Синхронизация оргструктуры настраивается в отдельном источнике данных; менять настройки входа через OIDC не нужно.

## Источники данных и синхронизация оргструктуры

Источник данных отвечает за синхронизацию оргструктуры, а источник идентификации по-прежнему отвечает за вход через OIDC или LDAP. Они настраиваются независимо: отключение источника данных не влияет на вход через OIDC.

1. Настройте существующий вход через OpenID Connect в разделе «Управление доступом → Источники идентификации».
2. В разделе «Управление доступом → Источники данных» добавьте источник DingTalk и выберите связанный источник идентификации OIDC.
3. Укажите CorpId, AppKey, AppSecret и ID корневого подразделения (обычно `1`). AppSecret шифруется отдельно, API никогда не возвращает его в открытом виде, а пустое поле при редактировании сохраняет прежнее значение.
4. Источник можно смонтировать под локальным подразделением. Интервал синхронизации по умолчанию — 30 минут, допускается 15–10080 минут; пустое значение означает только ручную синхронизацию.
5. После сохранения проверьте подключение и выполните первую синхронизацию. Приложению DingTalk нужны права на чтение подразделений и справочника сотрудников, и область доступа должна охватывать выбранное поддерево.
6. Когда пользователь входит через SSO, сотрудник находится по доверенной почте из OIDC, а подразделения и основное подразделение заполняются автоматически. Почту должен вести администратор, сотрудник не должен иметь возможности выдать себя за другого, и она должна совпадать с почтой в DingTalk. Если почты сотрудника нет, используется корпоративная почта.

Вход читает только локальный снимок справочника и не обращается к DingTalk. При включённой MFA принадлежность обновляется после успешного второго шага. Учётные записи, вошедшие до первой синхронизации, временно сохраняют доверенную почту и связываются после её завершения; редактируемая почта локального профиля в сопоставлении не участвует. Отсутствующие, повторяющиеся или уже привязанные к другой учётной записи адреса не создают новых привязок.

Привязка к сотруднику держится на внешнем ID сотрудника и не переходит к другому сотруднику при смене почты. Синхронизация учитывает принадлежность к нескольким подразделениям; основным остаётся прежнее основное подразделение, если оно действительно, иначе выбирается первое по стабильному порядку ID подразделений. Локальные подразделения, группы, должности и прямые назначения ролей сохраняются. Если назначить роль синхронизированному подразделению, пользователи наследуют её по обычным правилам, а перевод в другое подразделение обновляет права.

Как только появились снимок оргструктуры или учётные записи, ожидающие связывания, связанный источник идентификации, организация, приложение, корневое подразделение и точка монтирования фиксируются. Синхронизированные подразделения и принадлежность доступны только для чтения и не переопределяются вручную в управлении пользователями или оргструктурой. Исчезнувшие подразделения сохраняются, чтобы не потерять выданные права; когда сотрудник выходит из разрешённого справочника, принадлежность, которой управляет этот источник, снимается, но учётная запись автоматически не отключается. Источник данных, которому принадлежат подразделения, нельзя удалить напрямую — его можно отключить.

Синхронизация сначала получает все страницы и только затем атомарно применяет результат. При ошибке чтения, нарушении иерархии или изменении области доступа сохраняется последний успешный снимок; администратор проверяет результат по сводке синхронизации, списку проблем и журналу аудита. Если область доступа изменилась, сначала верните одобренную область, а затем запускайте синхронизацию.

Сейчас используется [официальный серверный SDK DingTalk](https://open.dingtalk.com/document/development/download-the-server-side-sdk); собственных HTTP-вызовов нет. Адаптеры поставщиков выдают единые снимки подразделений и сотрудников, поэтому будущий адаптер Feishu сможет повторно использовать ту же логику синхронизации, привязки и обновления прав.
