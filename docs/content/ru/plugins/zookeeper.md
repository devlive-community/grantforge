Плагин Apache ZooKeeper обеспечивает в GrantForge подключение к ансамблям, поиск путей znode и управление политиками. Идентификатор плагина и тип сервиса — `zookeeper`.

## Установка

Дистрибутив содержит плагин в `plugins/zookeeper`. Убедитесь в разделе **Управление платформой → Плагины**, что `zookeeper` включён; после обновления повторно просканируйте каталог плагинов. Плагин использует клиент ZooKeeper 3.9 в собственном загрузчике классов, отдельно от библиотек сервера.

## Добавление сервиса данных

1. Откройте **Права на данные → Сервисы данных**, добавьте сервис и выберите ZooKeeper (`zookeeper`).
2. Укажите строку подключения: серверы ансамбля с необязательным chroot, например `zk1:2181,zk2:2181,zk3:2181/kafka`. Клиент сам переключается между серверами.
3. Выберите аутентификацию, задайте znode для поиска и проверьте подключение (проверяется, что znode существует и его дочерние узлы можно перечислить), затем сохраните сервис.

| Параметр | Назначение |
| --- | --- |
| `zookeeper.connect` | Обязательная строка подключения: `host[:port]` через запятую, при необходимости с `/chroot`; chroot не может оканчиваться на `/` |
| `authentication` | `none` (по умолчанию), `digest` или `kerberos` |
| `username` | Digest: пользователь digest из ACL (без двоеточия); Kerberos: principal, например `grantforge@EXAMPLE.COM` |
| `password` | Пароль пользователя digest; хранится в зашифрованном виде |
| `keytab` | Kerberos: путь к keytab principal на сервере GrantForge |
| `zookeeper.sasl.client.username` | Kerberos: первая часть principal серверов, по умолчанию `zookeeper`, как в `zookeeper/<host>@<REALM>` |
| `zookeeper.server.principal` | Kerberos: полный principal серверов, если он другого вида, например `zookeeper/zk.example.com@EXAMPLE.COM` |
| `zookeeper.client.secure` | Подключаться ли к TLS-порту клиентов серверов, по умолчанию `false` |
| `zookeeper.ssl.trustStore.location` / `.password` / `.type` | Хранилище доверенных сертификатов для проверки серверов; пустое — доверять тому, чему доверяет Java сервера; тип `jks`, `pkcs12` или `pem` |
| `zookeeper.ssl.keyStore.location` / `.password` / `.type` | Хранилище ключей с клиентским сертификатом для серверов, которые его требуют |
| `session.timeout.ms` | Тайм-аут сеанса, по умолчанию `15000`, диапазон `2000..120000` |
| `connection.timeout.ms` | Ожидание только первоначального подключения и аутентификации, по умолчанию `10000` мс, диапазон `1000..60000`; не ограничивает последующие синхронные запросы |
| `request.timeout.ms` | Максимальное ожидание одного синхронного запроса, по умолчанию `8000` мс, диапазон `1000..60000` |
| `lookup.path` | Начальный znode для поиска и просмотра внутри chroot, по умолчанию `/`; например `/brokers`, просмотр ограничен им |
| `lookup.max.entries` | Максимум дочерних узлов, читаемых из одного znode за раз, по умолчанию `10000`, диапазон `1..100000` |

## Аутентификация

- **none**: без входа; читаются только znode, ACL которых открыт для `world:anyone`.
- **digest**: вход как `username:password`, что соответствует идентичностям `digest` в ACL ZooKeeper. Неверный пароль не отклоняется при входе: это другая идентичность, и защищённые znode показываются как доступ запрещён.
- **kerberos**: вход по SASL с keytab; `krb5.conf` сервера должен указывать на KDC. Каждый principal со своим keytab получает собственную секцию JAAS рядом с конфигурацией процесса, поэтому один GrantForge подключается к нескольким ансамблям под разными principal. Вход в Kerberos только по паролю пока не поддерживается.

При сохранении проверяются: формат строки подключения, пользователь и пароль для digest, principal и keytab для Kerberos, keytab и principal сервера только для Kerberos, а также диапазоны тайм-аутов и лимита.

При отключённом TLS пути и пароли хранилищ доверенных сертификатов и ключей должны быть пустыми. Для пароля хранилища требуется путь к соответствующему хранилищу. Для обоих хранилищ допустимы только типы `jks`, `pkcs12` и `pem`.

Пробелы в начале и конце паролей хранилищ TLS сохраняются. Конфигурация сервиса определяет режим TLS и хранилища для этого подключения, заменяя уже заданные в JVM параметры TLS и хранилищ ZooKeeper; сертификаты и имена хостов серверов по-прежнему проверяются.

## Просмотр znode

Выберите сервис в разделе **Права на данные → Политики** и нажмите **Обзор** рядом с `path`:

- Дочерние узлы выводятся постранично, по имени; znode со своими дочерними узлами можно открыть дальше.
- Для каждого znode показываются его ACL (`scheme:id:cdrwa`, как в инструментах ZooKeeper), размер данных и время изменения.
- Znode, ACL которого пользователь поиска не может прочитать, всё равно выводится по имени; при открытии показывается причина отказа.

Если znode удаляются во время постраничного просмотра, курсор всё равно продвигается по последнему просмотренному имени дочернего узла, даже если сам узел уже не существует. Список дочерних узлов не является снимком: одновременные добавления и удаления следуют семантике ZooKeeper и могут изменить последующие страницы.

При вводе пути предлагаются варианты; у несуществующего родителя их нет, а пути вне `lookup.path` отклоняются. Znode с числом дочерних узлов больше `lookup.max.entries` приводит к ошибке, а не к частичному выводу.

## Применение политик

Уровень ресурса один — `path`, типы доступа соответствуют правам ACL ZooKeeper: `read`, `write`, `create`, `delete` и `admin`; политики путей поддерживают рекурсию и исключения.

Плагин сервиса отвечает за управление, поиск и просмотр; агент внутри сервера применяет политики к ACL-маркерам через провайдер аутентификации SASL. Команда `mvn -pl agents/grantforge-agent-zookeeper -am package` создаёт один совместимый с Java 8 shaded JAR со всеми его зависимостями. В дистрибутиве он находится по пути `agents/zookeeper/grantforge-agent-zookeeper-<version>.jar`. Реализация рассчитана на API ZooKeeper 3.6–3.9, но совместимость с конкретными версиями ещё требует практической проверки. Это не означает, что вся матрица версий проверена или что приёмка для промышленной эксплуатации завершена.

### Развёртывание

1. Установите JAR в каталог `lib` **каждого сервера ZooKeeper**, включая все узлы, способные принимать клиентские запросы. Создайте **учётные данные Agent** в соответствующем сервисе данных GrantForge типа `zookeeper`. Сохраните токен в отдельном файле, доступном для чтения только учётной записи, от которой работает ZooKeeper; не записывайте сам токен в `zoo.cfg`.
2. Добавьте следующие параметры в `zoo.cfg` каждого сервера, заменив адрес, пути и идентификатор экземпляра из примера. `grantforge.server.url` (`http[s]://GrantForge`), `grantforge.token.file`, локальный `grantforge.cache.dir` и `grantforge.instance` обязательны. Учётная запись ZooKeeper должна иметь право записи в каталог кеша.

   ```properties
   authProvider.1=org.devlive.grantforge.zookeeper.agent.GrantForgeSaslAuthenticationProvider
   enableEagerACLCheck=false
   grantforge.server.url=https://GrantForge
   grantforge.token.file=/etc/zookeeper/grantforge.token
   grantforge.cache.dir=/var/lib/zookeeper/grantforge-cache
   grantforge.instance=zk-1
   grantforge.principal.mapping=short
   ```

3. Этот провайдер **заменяет штатный SASL-провайдер**; не оставляйте другой провайдер, зарегистрированный для той же схемы `sasl`, в какой-либо другой записи `authProvider.N`. Параметр `enableEagerACLCheck=false` обязателен: если проверка включена, регистрация провайдера отклоняется и маркер не разрешает доступ. Сохраните и проверьте штатную аутентификацию ZooKeeper с SASL, JAAS и Kerberos; агент не заменяет аутентификацию. Перезапустите серверы по процедуре обслуживания ансамбля.
4. При необходимости задайте `grantforge.signing.key.file` — путь к файлу с закреплённым доверенным открытым ключом подписи. Значение по умолчанию `grantforge.principal.mapping=short` преобразует `kafka/host@REALM` в `kafka`; `full` сохраняет полный principal. Пользователи в политиках должны соответствовать полученным идентичностям.

### ACL и ограничения

- Только ACL-маркер `sasl:grantforge` передаёт решение политикам GrantForge, например `sasl:grantforge:cdrwa`, где `c=create`, `d=delete`, `r=read`, `w=write` и `a=admin`. Остальные штатные ACL, включая другие SASL-идентичности, работают как обычно.
- Маркер отказывает в доступе, если агент не запущен, нет пригодного снимка политик, его `serviceType` отличается от `zookeeper` или ни одна политика не соответствует запросу/не разрешает доступ. **Это не глобальный запрет**: другие ACL, `world:anyone` или идентичность `super` всё ещё могут разрешить запрос.
- Политики сопоставляются с абсолютным целевым путём на сервере. Для `create`/`delete` это создаваемый/удаляемый znode, а не родитель, чья ACL проверяется. Для запросов с chroot путь в политике должен включать фактический префикс chroot: `/brokers` внутри chroot `/kafka` соответствует `/kafka/brokers`. Последовательный `create` проверяет абсолютный префикс запроса на сервере до добавления порядкового номера; последующие `read`/`delete` проверяют полное имя созданного узла.
- Штатные ACL не переносятся автоматически, а ACL не наследуются рекурсивно; новым znode нужно явно задавать ACL-маркер. Перед применением `setACL` проверьте разрешённые и отклонённые запросы на небольшом участке и сохраните независимый канал административного доступа. Не устанавливайте маркер на корневой узел без тщательной проверки, иначе можно заблокировать доступ.
- Сервер без агента сопоставляет `sasl:grantforge` со штатной SASL-идентичностью `grantforge`, а не с политиками. Поэтому агент необходим на всех узлах; частичное развёртывание не защищает ансамбль.
- У запросов записи, пересланных от follower/observer к leader, на этом интерфейсе провайдера может отсутствовать клиентское соединение, поэтому контекст `clientAddress` может быть пустым. Сквозное применение политик по IP клиента во всём ансамбле не гарантируется.
- Этот провайдер не может узнать окончательный результат запроса, поэтому не отправляет итоговые события аудита `AccessEvent` и не обеспечивает полный аудит доступа.
