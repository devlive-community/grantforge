**アクセス制御 → アイデンティティソース** で、ユーザーがログインに使用できるディレクトリまたはアイデンティティプロバイダーを設定します。この種のアカウントのパスワードはアイデンティティソースに保存され、GrantForge は保存も変更もできません。

![アイデンティティソース](/screenshots/identity-sources.png)

## LDAP / Active Directory

「アイデンティティソースの追加」をクリックし、種類には「LDAP ディレクトリ」を選択します。

| 設定 | 説明 |
| --- | --- |
| ディレクトリのアドレス | `ldap://` または `ldaps://`。複数のアドレスはスペースで区切り、フェイルオーバーを実現します |
| ユーザーの Base DN | 例: `ou=people,dc=example,dc=com` |
| 検索アカウント | ユーザーを検索するアカウント（Bind DN）とそのパスワードです。空欄の場合は匿名で検索します |
| ユーザーフィルター条件 | 既定値は `(&(objectClass=person)(uid={0}))` で、`{0}` はユーザーが入力した名前です |
| 属性 | ユーザー名、表示名、メールアドレス、一意識別子の属性です。既定値は OpenLDAP に合わせられており（`uid`、`cn`、`mail`、`entryUUID`）、Active Directory では `sAMAccountName` と `objectGUID` を入力します |
| 新しいユーザーのアカウントを自動作成 | 有効にすると、ディレクトリ内のユーザーが初回ログイン時にアカウントが作成されます |
| 同期間隔 | 空欄の場合は手動同期のみで、最短は 15 分です |
| ディレクトリから離脱したユーザーのアカウントを無効化 | 同期時にディレクトリに存在しなくなったユーザーを無効にします |

保存後、**接続テスト** をクリックして設定が正しいことを確認します。

ログイン時、GrantForge はまず検索アカウントでユーザーを検索し、次にユーザーが入力したパスワードをそのユーザーとしてディレクトリにバインドして検証します。

**同期**はディレクトリ内の新しいユーザーのアカウントを作成し、既存アカウントの氏名とメールアドレスを更新し、設定に応じて離脱したユーザーを無効にします（あわせてそのセッションも終了します）。同期の結果はアイデンティティソースのカードに表示されます。

## OpenID Connect

種類に「OpenID Connect」を選択すると、Keycloak、Azure AD、Okta、別の GrantForge などに連携できます。

| 設定 | 説明 |
| --- | --- |
| Issuer アドレス | プロバイダーの発行者アドレスです。GrantForge はこのアドレスのディスカバリドキュメントからエンドポイントとキーを取得します |
| クライアント ID / シークレット | プロバイダーに登録したクライアントです。シークレットがない場合は公開クライアントとして動作し、PKCE を使用します |
| コールバックアドレス | ページに表示される `<GrantForge>/api/v1/auth/federated/callback/<エンコーディング>` のアドレスで、プロバイダーのクライアントに登録する必要があります |
| スコープとクレーム | 既定値は `openid profile email` です。ユーザー名、表示名、メールアドレスはそれぞれ `preferred_username`、`name`、`email` クレームから取得します |
| 電話番号クレーム | 既定では `phone`（Casdoor）を読み取ります。ほかのプロバイダーでは `phone_number` を設定できます。電話番号を同期するには scope に `phone` を含めます。ログイン時にプロバイダーが番号を返さない場合は既存の番号を保持します |
| アバター URL | OIDC 標準の `picture` クレームから同期します。scope に `profile` を含める必要があります。返されない場合は既存のアバター URL を保持します |
| 認可リクエストの追加パラメーター | 任意の JSON オブジェクトで、値はすべて文字列にします。たとえば Casdoor では `{"provider_hint":"github"}` で設定済みのプロバイダーを指定できます。パラメーターはブラウザーのアドレスに表示されるため、シークレットは入れないでください |

プロトコルの主要パラメーター（`state`、`nonce`、`redirect_uri`、PKCE パラメーターを含む）は GrantForge が管理し、追加パラメーターで上書きすることはできません。

有効にすると、ログインページに「<名前> でログイン」ボタンが表示されます。ユーザーはプロバイダーでログインしたあと GrantForge に戻り、二段階認証を有効にしたアカウントは認証コードの入力も必要です。

## アカウントのルール

- アイデンティティソースのユーザーの一意識別子（LDAP は `entryUUID`/`objectGUID`、OIDC は `sub`）は 1 つの GrantForge アカウントに対応し、名前が変わっても対応関係は変わりません。
- ローカルに同名のアカウントが既にある場合、**自動的には関連付けられず**、ログインは拒否されます。管理者が先にローカルアカウントの名前を変更または削除する必要があります。これにより、ディレクトリ内の同名ユーザーが既存アカウントを引き継ぐ事態を防ぎます。
- アカウントを自動作成しないアイデンティティソースでは、既に関連付けられたユーザーのみがログインできます。
- アイデンティティソースを無効にすると、そのユーザーはログインできません。アカウントが使用中のアイデンティティソースは削除できません。
- アイデンティティソースのアカウントには、通常どおりロールを割り当て、二段階認証を有効にできます。

組織構造の同期は独立したデータソースで設定し、OIDC ログインの設定を変える必要はありません。

## データソースと組織構造の同期

データソースは組織構造の同期を担い、アイデンティティソースは引き続き OIDC または LDAP のログインを担います。両者は別々に設定し、データソースを無効にしても OIDC ログインには影響しません。

1. 「アクセス制御 → アイデンティティソース」で既存の OpenID Connect ログインを設定します。
2. 「アクセス制御 → データソース」で DingTalk のデータソースを追加し、関連付ける OIDC アイデンティティソースを選びます。
3. CorpId、AppKey、AppSecret と起点の部署 ID（通常は `1`）を入力します。AppSecret は個別に暗号化して保存され、API が平文を返すことはありません。編集時に空欄のままにすると元の値を保持します。
4. ローカルの部署の下にマウントできます。同期間隔の既定値は 30 分で、15–10080 分を指定できます。空欄にすると手動同期のみになります。
5. 保存後に接続をテストし、初回同期を実行します。DingTalk アプリケーションには部署と従業員の連絡先を読み取る権限が必要で、その許可範囲は選んだサブツリーを含んでいなければなりません。
6. ユーザーが SSO でログインすると、信頼できる OIDC のメールアドレスで従業員を照合し、部署と主所属部署を自動で設定します。メールアドレスは管理者が管理し、従業員が他人になりすまして使えないものであり、DingTalk のメールアドレスと一致している必要があります。従業員のメールアドレスがない場合は企業メールアドレスを使います。

ログインはローカルの連絡先スナップショットだけを参照し、DingTalk にはリクエストしません。MFA が有効な場合は、2 段階目の認証に成功してから所属を更新します。初回同期より前にログインしたアカウントは信頼できるメールアドレスを一時保存し、同期完了後に関連付けます。ローカルで編集できるプロフィールのメールアドレスは照合に使いません。欠落している、重複している、または別のアカウントに紐付け済みのメールアドレスからは新しい紐付けを作りません。

従業員との紐付けは外部の従業員 ID で固定され、メールアドレスが変わっても別の従業員に移ることはありません。同期は複数部署への所属も扱います。主所属部署は有効な元の主所属部署を優先して残し、なければ安定した部署 ID の順で選びます。ローカルの部署、ユーザーグループ、ポジション、直接のロール付与は保持されます。同期された部署にロールを割り当てると、ユーザーは既存の付与ルールに従ってロールを継承し、異動すると権限も更新されます。

組織スナップショットや関連付け待ちのアカウントができた後は、関連付けたアイデンティティソース、企業、アプリケーション、起点の部署、マウント先を変更できません。同期された部署と所属は読み取り専用で、ユーザー管理や組織管理から手動で上書きすることはできません。消えた部署は既存の付与を守るために残します。従業員が許可された連絡先から外れると、このデータソースが管理する所属を外しますが、アカウントを自動で無効にはしません。同期された部署を持つデータソースは直接削除できず、代わりに無効にできます。

同期はすべてのページを取得してからアトミックに適用します。読み取りの失敗、階層の異常、許可範囲の変化があった場合は前回成功したスナップショットを保持し、管理者は同期の概要、異常の一覧、監査ログで結果を確認できます。許可範囲が変わった場合は、元の承認済み範囲に戻してから同期してください。

現在は [DingTalk 公式のサーバー SDK](https://open.dingtalk.com/document/development/download-the-server-side-sdk) を使い、HTTP 呼び出しを独自に実装していません。プロバイダーのアダプターは共通の部署と従業員のスナップショットを出力するため、今後 Feishu のアダプターを追加しても同じ同期、紐付け、権限更新のロジックを再利用できます。
