O 2026.2.0 estende as permissões de sistemas externos do 2026.1.0 ao Apache Hive, Apache Kafka, Apache HBase, Trino e Apache Hadoop YARN, com agentes que as aplicam. A lista completa de mudanças está na [comparação no GitHub](https://github.com/devlive-community/grantforge/compare/v2026.1.0...v2026.2.0).

## Apache Hive

- Um plug-in de serviço Hive: bancos de dados, tabelas, colunas, UDFs, URLs, o serviço HiveServer2 e replicação, com os tipos de acesso do Hive como o Apache Ranger os define; veja [Apache Hive](/pt-br/plugins/hive/).
- Um agente HiveServer2 que verifica cada instrução, filtra os resultados de `SHOW`, mascara colunas e filtra linhas; veja o [agente Hive](/pt-br/external/hive-agent/).
- UDFs temporárias são concedidas no escopo global apenas a `tempudfadmin`, como faz o Apache Ranger, pois executam código escolhido pelo usuário.

## Apache Kafka

- Um plug-in de serviço Kafka: tópicos, grupos, IDs transacionais, o cluster, tokens de delegação e usuários SCRAM, com os tipos de acesso e implicações próprios do Kafka; veja [Apache Kafka](/pt-br/plugins/kafka/).
- Um autorizador de broker e de controller que verifica cada requisição; veja o [agente Kafka](/pt-br/external/kafka-agent/).

## Apache HBase

- Um plug-in de serviço HBase: namespaces, tabelas, famílias de colunas e colunas, além do escopo global para operações sobre todo o cluster; veja [Apache HBase](/pt-br/plugins/hbase/).
- Um coprocessador para o master e os region servers que verifica as operações, retorna apenas as colunas que um usuário pode ler e oculta o que ele não pode ver; veja o [agente HBase](/pt-br/external/hbase-agent/).

## Trino

- Um plug-in de serviço Trino: catálogos, schemas, tabelas, colunas, funções, procedimentos e propriedades de sessão; veja [Trino](/pt-br/plugins/trino/).
- Dois controles de acesso do sistema, um para Trino 470 a 478 e outro para Trino 479 e posteriores, que verificam consultas, filtram linhas e mascaram colunas; veja os [agentes Trino](/pt-br/external/trino-agent/).

## Apache Hadoop YARN

- Um plug-in de serviço YARN: filas e aplicações, com os tipos de acesso `submit_app` e `admin_queue` do YARN; veja [Apache Hadoop YARN](/pt-br/plugins/yarn/).
- Um provedor de autorização no ResourceManager que decide envio, filas e administração do cluster por política, com condições sobre endereços de clientes; veja o [agente YARN](/pt-br/external/yarn-agent/).

## Motor de políticas e agentes

- As políticas decidem acessos abaixo de um recurso: listar um banco de dados conta as políticas de tabelas do usuário, e o novo tipo de acesso `_any` é permitido quando algum acesso ao recurso ou abaixo dele é permitido.
- As políticas respondem se um usuário pode fazer algo com algum recurso de um nível, como o Kafka pergunta antes de produtores idempotentes gravarem.
- Os agentes agrupam acessos permitidos idênticos de uma janela de tempo em um único evento de auditoria com contagem e o momento do último; as recusas são registradas de imediato.
- Os agentes podem mostrar suas políticas de acesso nos termos do próprio sistema.
- A API de plug-ins 1.2.0 fornece os realms do Kerberos uma vez a todos os plug-ins, que não sobrescrevem mais o `krb5.conf` uns dos outros.

## Documentação e publicação

- Os plug-ins e agentes de YARN, Hive, Kafka, HBase e Trino estão documentados em todos os onze idiomas.
- O README lista os componentes suportados e as versões verificadas pelos testes de integração.
- As tags de versão executam a CI completa e a publicação aguarda essa execução; a distribuição é compilada em paralelo; o npm publica por publicação confiável (trusted publishing).
- Versões sem registro de publicação são recusadas ao criar a tag; a CI executa, após um gate Java comum, apenas os jobs que a mudança exige.

## Correções

- Os índices do PostgreSQL são preparados após a carga de dados, para que as chamadas de API cronometradas rodem sobre tabelas analisadas.
- Os testes dos jars do agente ZooKeeper rodam após o empacotamento.
- Os deploys do Maven pulam os testes de integração; um timeout da JVM bifurcada no agente HDFS 3.2 havia feito o deploy no GitHub Packages falhar.
- O pacote npm declara seu repositório, para que o npm possa verificar a proveniência.
